# 経緯と、「たまたま動いているだけかもしれない」点

このリポジトリの中身は、設計図から作ったものではない。**動かしては観察し、仮説を立てて直す**ことを繰り返した結果の、
最終状態の記録である。途中で外れた仮説も多く、いま動いているのは、確認できた範囲では動いているだけで、
理由を全部理解した上で動いているわけではない。

## 進め方

- 窓が出るか、文字が出るか、遅れるかは、**人が実際の画面を見て**報告し、それをログ（`/mnt/wslg/weston.log` ほか）と突き合わせた。
  自動テストは、サブサーフェスと frame callback の小さなクライアント（`test/subsurface-test/`）以外に無い。
- msrdc（Windows 側）は中身を見られない。**振る舞いは、Weston 側のログと、Windows 側から見える窓の属性からの推測**である。
  ドキュメントがあるわけではないので、msrdc や WSLg の更新で変わる可能性がある。

## 時系列

1. **出発点**: kitty と curl を .deb で入れて使っていた。WSLg 上の kitty の日本語入力に遅延を感じ、別のバージョンと
   比べても差がなかったので、スタックの別の層を疑った。
2. **Weston の対応状況を調べた**: WSLg の Weston 9 は `text-input-v1` / `input-method-v1` しか出さず、`input_method` は
   Weston が起動したクライアントにしか bind させない。kitty は `text-input-v3` だけを話す。遅延の話は、
   「Wayland ネイティブで動かすこと自体に価値がある」という判断に置き換わった。
3. **選択肢の比較**: Weston の設定への介入、別のコンポジタ（KWin / Mutter / labwc / sway）を入れ子で動かす、Weston そのものを
   差し替える。入れ子の KWin は、Weston 9 に `wp_single_pixel_buffer_manager_v1` が無く起動しなかった。
   Weston を upstream ベースに差し替え、その上で KWin を入れ子にする案を選んだ（MR !1667 を使う）。
4. **MR を当ててビルド、WSLg の外で試験**: システムディストロに触れる前に、専用のソケットとポートで Weston を動かし、
   Xwayland などを確認した。ここで、NULL 参照（0001）、二重解放（0002）、Xwayland の 4 連鎖のバグ（0003）が出た。
5. **システムディストロへ差し込み、msrdc と繋ぐ**: `/usr/bin/weston` をラッパーに置き換えた。
   - 「NLA セキュリティしか対応しない」で切断 → 標準 RDP セキュリティ（0004）
   - タスクバーに `[WARN:COPY MODE]` だけで窓の中身が無い → Ubuntu の FreeRDP が gfxredir 無しなのを突き止め、自前ビルド
   - 2 枚目のモニタで落ちる → 0005
6. **WSL を再起動すると差し替えが消える**ことが分かり、systemd のサービスで毎回適用し直すようにした。
   最初の実機での起動は、WSLGd の `xset` との競合でデッドロックして GUI が出なかった（[pitfalls.md](pitfalls.md)）。
   待つ条件を足して直した。
7. **余計なタスクバーアイコン 2 つ**: 最初の直し方（0006）は効かず、原因を見直して 0007 にした。
8. **入れ子の KWin**: 黒い窓のままで、原因を探して、サブサーフェスで全面が覆われた親サーフェスに frame callback が来ないこと
   だと分かった（0008）。直して KWin 内の kitty が見えたが、外側の窓に枠が無い（移動もリサイズもできない）。
   窓のスタイルを変えて枠を出そうとしたが、msrdc がスタイルを上書きするので**効かなかった**（変更は戻した）。
   **直接起動の Wayland 版 kitty のほうが、透過も効いて使い心地が良い**と分かり、入れ子の KWin はやめた。
9. **`text-input-v3` を Weston に足した**（0009）。動いたが、画面が 1 ストローク遅れて見えた。
   - 仮説 1: ack の後に再描画が予約されない → 直したが、**これだけでは体感は変わらなかった**（コードは正しいと考えて残してある）。
   - 窓を小さくすると改善 → 更新量が効いていると推測し、変わった範囲だけを送る方式にした（0010）。これが効いた。
   - その確認中に、カーソル周りのアサーションで Weston が落ちた。アサーションを避ける形で直した（0011）。
10. Windows のショートカットから起動するランチャーを Wayland 版にして、現在に至る。

## たまたま動いているだけかもしれない点

| 点 | 内容 |
| --- | --- |
| 0010 の差分送信 | msrdc が共有メモリのうち `dirtyRect` だけを読む、という**仮定**の上にある。仮定が外れる条件（高 DPI、スケーリング、アルファ付きの窓、複数モニタ）では試していない。 |
| 0010 の再描画予約 | 効果を確認できていない。論理的には正しいと考えて入れているだけ。 |
| 更新のスキップ条件 | `currentFrameId − acknowledgedFrameId >= 2` は、MR のままで、窓ごとに present ID が増える事実とは噛み合っていない。差分送信で当たりにくくしただけで、根本は直していない。 |
| 0011 | 原因ではなく症状（アサーション）を避けているだけ。kitty のカーソル用サーフェスが、先に RAIL の窓として扱われる経緯は未調査。 |
| 0006 と 0007 | 「内容の無い窓を出さない」判定は、実測で効いた条件を選んだもの。他のクライアントで、正しく表示すべき窓を隠す可能性は排除できていない。 |
| 終了時の SEGV | カスタム版を SIGTERM で止めると、`rdp-backend.so` 内で落ちることがある。原因は未調査。 |
| `text-input-v3` の変換 | serial の扱いなどは、kitty と fcitx5（日本語入力）の組み合わせで動く範囲しか確認していない。GTK4、Qt6、他の IME は未確認。`keysym` などは無視している。 |
| 長時間の動作 | 数時間〜数日の動作、メモリの増え方（差分用の一時バッファは窓ごとに持つ）、スリープからの復帰は未確認。 |
| 環境依存 | 元の Weston の sha256、WSLG のバージョン、msrdc の挙動に依存している。WSL や WSLg の更新で、いつでも壊れうる。 |
| MR の古さ | MR !1667 は止まっていて、最新の Weston 15.0.1 には 9 ファイルで衝突する。このベースに固定している。 |

## 参考: 判断の記録

- 「入れ子の KWin」から「Weston に `text-input-v3` を足す」への転換は、**使い心地の比較**（直接起動の Wayland 版 kitty のほうが良い）
  で決めた。技術的に KWin が不可能だったわけではない。
- 公開を急がず、「実験段階で、通しの手順は試していない」と明記した上で出すことにした。
